# Cycle guard: запрет повторных агентских циклов

Этот документ фиксирует обязательные ограничения для Codex, Grok и других
делегированных исполнителей в `D:\DE_project`. Его цель — не допустить
повторения попыток без достаточного нового прогресса.

## Инцидент 2026-08-02

После первого неуспешного canary orchestration продолжил работу серией из
**8 Grok-run'ов**:

1. Stage 4, попытка 1 — отменена политикой команд.
2. Stage 4, попытка 2 — baseline и producer прошли, verifier корректно упал.
3. Local fix, попытка 1 — отменена во время проверки.
4. Local fix, попытка 2 — отменена во время проверки.
5. Общая очистка `__pycache__` — отменена политикой команд.
6. Отдельная очистка main-pack `__pycache__` — завершена.
7. Отдельная очистка canary2 `__pycache__` — завершена.
8. Clean reinstall — запущен до закрытия всей цепочки.

Пять запусков были повторными или служебными. Декомпозиция мелкой очистки в
новые агентские запуски создала видимость работы, но не приблизила основной
production gate пропорционально потраченному времени. Это считается
процессным циклом и недопустимо.

## Жёсткий лимит попыток

Для одного именованного atomic item разрешены:

- одна основная попытка;
- одна дополнительная попытка только после доказанной причины сбоя и с одним
  явно изменённым параметром: форма команды, permission rule, transport,
  диагностическая гипотеза или ограниченный scope.

После второй неуспешной попытки item немедленно получает статус `BLOCKED` или
`FAILED`. Третья попытка запрещена без нового прямого разрешения пользователя.
Новый prompt, RunId или дробление той же операции на меньшие части сами по себе
не считаются новой гипотезой.

## Обязательная карточка попытки

Перед каждым delegated run оркестратор обязан кратко зафиксировать:

- имя atomic item;
- номер попытки: `1/2` или `2/2`;
- ожидаемое изменение состояния;
- единственный критерий PASS;
- предыдущую failure signature, если это retry;
- конкретное отличие retry от предыдущей попытки;
- действие при FAIL: `STOP`, без автоматического продолжения.

Если один из пунктов отсутствует, запуск запрещён.

## Что считается прогрессом

Прогрессом считается только хотя бы одно из следующего:

- требуемое состояние действительно изменилось;
- новая проверка закрыла ранее открытый gate;
- получена новая диагностическая информация, исключающая конкретную гипотезу;
- создан один завершённый, проверяемый артефакт, необходимый для текущего item.

Не считаются прогрессом:

- новый RunId с тем же действием;
- повторное чтение уже подтверждённого состояния;
- повторный hash/status/HEAD refresh без изменения входных данных;
- отдельный агентский run для удаления cache, временного файла или другого
  housekeeping residue;
- переформулировка прежнего blocker;
- смена prompt без изменения failure hypothesis.

## Housekeeping не порождает новые циклы

Очистка `__pycache__`, временных файлов и диагностического residue должна быть
частью исходного bounded task. Если executor не смог выполнить такую очистку в
оставшейся второй попытке:

1. основной результат сохраняется как есть;
2. residue точно перечисляется в отчёте;
3. новые executor-run'ы для той же очистки не запускаются;
4. дальнейшее действие возможно только по прямому запросу пользователя.

Housekeeping никогда не оправдывает превышение лимита `2`.

## Запрет фоновых mutation-run'ов

Фоновый исполнитель, способный менять файлы или runtime, запрещён, если его
нельзя атомарно остановить при пользовательском hard stop. Для write/runtime
работы используются только bounded foreground-вызовы либо механизм, который
гарантированно прекращается вместе с активным turn.

Нельзя запускать следующий executor, пока предыдущий жив, ожидает timeout или
не имеет окончательного результата. Длительный `kubectl wait` после уже
зафиксированного `Failed` Job должен быть прекращён внутри той же попытки; он не
является основанием для нового run.

## Fail-closed после проверки

Если canary, verifier, soak, rollback или другой gate вернул `FAIL`:

1. следующий production stage не запускается;
2. выполняется максимум один read-only диагностический проход;
3. исправление оформляется как один новый atomic item с собственным лимитом
   `1 + 1`, только если root cause доказан;
4. прежний failed evidence не удаляется и не переписывается;
5. raw retry того же workload запрещён.

## Правило остановки

Работа немедленно прекращается при любом из условий:

- пользователь упомянул цикл, повторение, остановку или потребовал паузу;
- исчерпан лимит двух попыток;
- нет нового проверяемого изменения состояния;
- следующий шаг является только housekeeping;
- исполнитель отменён второй раз с той же failure signature;
- требуется расширение scope, remote/destructive authority или новый выбор
  пользователя.

После остановки ответ содержит только:

- достигнутое состояние;
- точный blocker/failure signature;
- число использованных попыток;
- подтверждение, что новые run'ы не запущены.

## Короткий preflight перед делегированием

```text
Atomic item: <name>
Attempt: 1/2 | 2/2
Expected state delta: <one concrete change>
PASS evidence: <one decisive check>
Previous failure: <signature or none>
Changed dimension: <exactly one or initial>
On failure: STOP
```

Отсутствие этого блока означает автоматический запрет на делегирование.
